# Notification Center Implementation Plan

> **For Hermes:** Use `church-app-feature-delivery` and `subagent-driven-development` skills to implement this plan task-by-task.

**Goal:** Build a ward-scoped notification center where users choose in-app and/or email subscriptions, review notification details, and navigate to the related meeting, calling, member, note, announcement, or administrative record.

**Architecture:** Keep domain events in the existing transactional outbox. Add user subscriptions and recipient-specific in-app notifications as separate tables. The event processor determines recipient permissions and subscriptions before creating in-app notifications or email delivery jobs. In-app notifications and email delivery must never bypass ward isolation or note visibility rules.

**Tech Stack:** Next.js App Router, React, TypeScript, PostgreSQL, Drizzle schema/migrations, existing `event_outbox` and BullMQ notification worker, Vitest, React Testing Library.

---

## 1. Product decisions

### 1.1 Channels

Each event type has two independent channel controls:

- In app
- Email

Selecting either channel subscribes the user. Selecting both delivers through both channels. No separate `subscribe` checkbox is needed.

Future channels such as push notifications can use the same subscription model, but are out of scope for the first implementation.

### 1.2 Ward scope

Subscriptions and notifications are scoped by `ward_id`.

A user may have different subscriptions in different wards. Support administrators may access another ward only through the existing support-access workflow and must not receive that ward's notifications merely because they can technically access it.

### 1.3 Event categories

Initial categories:

- Callings
- Membership
- Meetings
- Notes and comments
- Announcements
- Calendar
- Access and administration
- System alerts
- Reminders

### 1.4 Default subscriptions

Create defaults when a user first receives access to a ward. Defaults must be explicit and editable:

- Calling suggested: in app and email
- Calling sustained, set apart, or released: in app and email
- Membership import completed: in app
- Membership import failed: in app and email
- Meeting created: in app
- Meeting changed: in app
- Meeting published or republished: in app and email
- Note or comment added: in app
- Direct mention: in app and email
- Access request: in app and email for authorized users
- System failure: in app and email for authorized users
- Reminders: in app

Do not send email on every meeting autosave or every minor field change.

## 4. Data model

### 4.1 `notification_subscription`

Add a ward-scoped table:

```text
id                 UUID primary key
ward_id            UUID not null
user_id            UUID not null
category           TEXT not null
 event_type        TEXT not null
channel            TEXT not null -- IN_APP or EMAIL
enabled            BOOLEAN not null default true
created_at         TIMESTAMPTZ not null default now()
updated_at         TIMESTAMPTZ not null default now()
```

Use exact column naming without the accidental space shown above when implementing: `event_type`.

Constraints:

- `channel IN ('IN_APP', 'EMAIL')`
- Unique `(ward_id, user_id, event_type, channel)`
- Foreign keys to `ward` and `user_account`
- RLS enabled and forced
- RLS policy requires current ward context
- Queries must also verify the requesting user owns the subscription

`category` is denormalized for efficient settings-page grouping. Event-type validation remains application-level through the centralized event registry.

### 4.2 `user_notification`

Add a ward-scoped table:

```text
id                  UUID primary key
ward_id             UUID not null
recipient_user_id   UUID not null
source_event_id     UUID not null
 event_type         TEXT not null
aggregate_type      TEXT not null
aggregate_id        UUID not null
title               TEXT not null
summary             TEXT not null
details             JSONB
severity            TEXT not null default 'info'
target_url          TEXT
read_at             TIMESTAMPTZ
 dismissed_at       TIMESTAMPTZ
created_at          TIMESTAMPTZ not null default now()
```

Use exact column names without the accidental spaces shown above when implementing: `event_type` and `dismissed_at`.

Constraints and indexes:

- Foreign key to `ward`
- Foreign key to `event_outbox` through `source_event_id`
- Unique `(recipient_user_id, source_event_id)` to prevent duplicate recipient notifications
- Index `(recipient_user_id, ward_id, created_at DESC)`
- Index `(recipient_user_id, ward_id, read_at)` for unread counts
- RLS enabled and forced
- RLS policy requires current ward context and recipient user identity

Do not copy private note text into broadly accessible event payloads. Store only the minimum details needed to render an authorized notification.

### 4.3 Email delivery integration

Extend existing `notification_delivery` rather than creating a second delivery table where possible:

- Keep `channel = 'webhook'` for existing outbound webhook behavior.
- Add `channel = 'email'` for user email deliveries.
- Add recipient metadata only if required by the email provider.
- Preserve unique `(event_outbox_id, channel)` behavior only if one event has one email delivery. If each recipient requires separate delivery status, use `user_notification_id` as the delivery key or add a recipient-specific unique constraint.

Preferred design: create email delivery records from `user_notification`, because one event can notify many users and each recipient can succeed or fail independently.

## 5. Domain modules

Create a centralized notification domain under `apps/web/src/notifications/`:

- `events.ts` — event type/category registry and typed event payloads
- `subscriptions.ts` — subscription reads, upserts, defaults, and authorization
- `user-notifications.ts` — recipient notification creation, listing, read, and dismissal
- `recipients.ts` — permission-aware recipient resolution
- `format.ts` — titles, summaries, detail payloads, severity, and target URLs
- `visibility.ts` — note/comment visibility checks
- `email.ts` — email payload creation and provider/queue integration

Keep route handlers thin. Business rules belong in these modules and must be testable without rendering React pages.


The union must eventually include every event in the registry. Do not let arbitrary client-provided event names control subscriptions.

## 6. Event processing flow

Implement this flow:

1. Existing business action validates auth, ward, permissions, and input.
2. Business transaction changes the domain record.
3. Same transaction inserts one deduplicated `event_outbox` row.
4. After commit, existing queue code schedules processing.
5. Processor loads the event under ward context.
6. Processor determines eligible recipients from ward roles and event-specific permissions.
7. Processor checks each recipient's in-app and email subscriptions.
8. Processor creates idempotent `user_notification` rows for in-app recipients.
9. Processor creates asynchronous email delivery jobs for email recipients.
10. Processor records failures without exposing sensitive event payloads.

Do not notify every ward user by default. Recipient policy must be explicit per event type.

Examples:

- Calling suggestion: users with calling-management permission, plus explicitly configured participants where appropriate.
- Membership update: users with membership-view permission.
- Meeting change: users with meeting-edit or meeting-view permission, depending on sensitivity.
- Private note: creator and users explicitly authorized to read it.
- Leadership note: users who can use internal notes and users who can read that specific note.
- Access request: authorized ward administrators.
- System failure: support administrators or configured operational users.

## 7. API routes

### 7.1 Subscription preferences

Create:

```text
GET  /api/w/[wardId]/notification-subscriptions
PUT  /api/w/[wardId]/notification-subscriptions
```

`GET` returns grouped event types with both channel states. `PUT` accepts a batch of explicit updates:

```json
{
  "subscriptions": [
    {
      "eventType": "MEETING_PUBLISHED",
      "channel": "IN_APP",
      "enabled": true
    },
    {
      "eventType": "MEETING_PUBLISHED",
      "channel": "EMAIL",
      "enabled": false
    }
  ]
}
```

Requirements:

- Authenticated session
- Active ward validation
- User can modify only their own subscriptions
- Event type and channel validation
- Idempotent upsert
- Audit subscription changes if project policy requires user-preference auditing
- Return standard error shape

### 7.2 User notifications

Create:

```text
GET    /api/w/[wardId]/notifications
PATCH  /api/w/[wardId]/notifications/[notificationId]
POST   /api/w/[wardId]/notifications/mark-all-read
```

`GET` supports:

- `filter=all|unread`
- `category=...`
- `limit` with safe clamp
- Cursor pagination later; offset pagination is acceptable for first version

`PATCH` supports only safe state changes:

```json
{ "action": "read" }
```

or:

```json
{ "action": "dismiss" }
```

Every query must include both `ward_id` and recipient user identity. Never trust notification IDs alone.

### 7.3 Email preferences

Email delivery should use the same subscription endpoint. Add account-level email readiness checks:

- Email address exists
- Account is active
- User has not globally disabled email
- Email provider is configured

Do not silently pretend email is enabled if delivery configuration is unavailable. Display a clear settings warning.

## 9. Privacy and security requirements

- Enforce ward isolation through API checks and PostgreSQL RLS.
- Enforce recipient ownership on every notification read/update query.
- Check source-record visibility before creating notification details.
- Never expose private note text in notification titles, summaries, email subjects, logs, or diagnostics to unauthorized users.
- Do not leak existence of restricted members, callings, notes, or access requests.
- Email is less controlled than the app; email content must be concise and privacy-safe.
- Use generic email text for sensitive events, with a secure link to the app.
- Audit administrative changes to notification subscriptions if required by the existing audit policy.
- Prevent open redirects: `target_url` must be generated from approved internal routes, never accepted from the client.
- Rate-limit mark-read and preference update endpoints if abuse becomes possible.
- Expire or dismiss stale notifications according to a documented retention policy.

Church policy or leadership workflow questions should be checked against official Church sources, especially the General Handbook, rather than inferred from application behavior.

## 12. Acceptance criteria

- User can open notification settings for active ward.
- Every enabled event type exposes independent In app and Email checkboxes.
- User can save either channel, both channels, or neither.
- Defaults are created and can be restored.
- User can view recent notifications in `/notifications`.
- Unread count appears in authenticated navigation.
- Notification entries expand to show details.
- Notification entries navigate to approved related records.
- Mark read, mark all read, and dismiss work without affecting other users.
- Calling, membership, meeting, note/comment, announcement, access, and system events use explicit recipient rules.
- Unauthorized users cannot receive or view restricted notifications.
- Cross-ward reads and writes fail at API and RLS layers.
- Retried events do not create duplicate user notifications.
- Email deliveries are asynchronous and independently tracked per recipient.
- Email content does not expose private or unauthorized information.
- Existing webhook diagnostics continue working or move to an authorized diagnostics page.
- Tests, typecheck, dependency graph checks, build, and diff checks pass.

## 13. Risks and tradeoffs

### Notification volume

Sending every meeting field update creates noise. Use meaningful update events, publish events, and reminders instead of raw autosave events.

### Privacy

Notifications can leak sensitive information more easily than source pages, especially through email previews. Keep details minimal and permission-aware.

### Recipient complexity

Different events require different roles and visibility rules. Centralize recipient policy rather than embedding recipient queries in route handlers.

### Email operations

Email introduces provider credentials, bounce handling, retry behavior, and unsubscribe requirements. Build in-app notifications first, then enable email with an explicit provider configuration and clear failure state.

### Existing diagnostics terminology

Current `/notifications` is operational diagnostics. Converting it directly risks confusing normal users and administrators. Prefer a user center at `/notifications` and move diagnostics behind a clearly named settings/admin route.

### Retention

Unread notifications can accumulate indefinitely. Start with pagination and dismissal. Add documented retention cleanup after observing real usage.

## 14. Open decisions before implementation

1. Which ward roles receive each event category by default?
2. Should users receive notifications for actions they performed themselves?
3. Should `MEETING_UPDATED` notify all meeting viewers or only editors?
4. Are comments a new data model or another name for internal notes?
5. Which email provider will be self-hosted or externally managed?
6. Should email be enabled immediately or after in-app notification validation?
7. What retention period applies to read and dismissed notifications?
8. Which reminders are useful enough to ship in first release?
9. Should support administrators receive notifications only while explicitly supporting a ward?
10. Which Church workflow details require confirmation against the General Handbook before encoding as defaults?

Recommended implementation sequence: **in-app subscriptions and notifications first, email delivery second, reminders third.**
